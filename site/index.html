Why it is different

Plenty of tools write code from a prompt. Karigor runs the whole job.

01

It owns the whole lifecycle

Specify, design, plan, build, verify, release, and then watch production and fix what breaks. Not “here is a repo, good luck”.

02

Reliability comes from process, not trust

A small, deterministic kernel runs a real software process. Nothing moves forward without mechanical evidence: tests green, security scan clean, a healthy preview, a verified rollback. Agents will make mistakes; the gates stop them reaching you.

Gates

No step moves forward on an agent’s word.

Three gates stand between your idea and a live app. Each one needs evidence: some run the real thing, others are judged by a reviewer and a skeptic who must cite proof. Pick a gate to see what it checks.

  1. youAn ideaOne sentence, in your own words. Nobody asks you a technical question.
  2. product owner · architectSpec & designWho uses it and what each may do. Every assumption recorded.
  3. no evidence → retry
  4. planner · developerBuildSmall pieces, one commit each, in a real git repo.
  5. a failure → the ladder
  6. unhealthy → not promoted
  7. liveYour appA real address you can share.

Then it keeps working. App errors, downtime, vulnerable libraries and your feedback become fixes, and every fix goes back through the same gates.

Reviewed checks the plan before any code is written.

  • spec-completejudgedA reviewer finds the spec complete enough to design and build from.
  • architecture-soundjudgedThe design names the roles and modules and fits the spec.
  • schema-validmechanicalEvery document an agent produced matches its schema.
  • budget-okmechanicalThe work so far fits the cost tier you chose.

When it fails

The role is shown exactly what was objected to and what it wrote last time, then tries again. A verdict that cites no evidence counts as a fail, so a judge cannot wave work through.

Proven runs on every piece of the build, not once at the end.

  • tests-passmechanicalThe project’s real tests run green.
  • lint-cleanmechanicalThe code passes the linter.
  • build-succeedsmechanicalThe production build completes.
  • security-scan-cleanmechanicalNo leaked secrets, no vulnerable libraries.
  • diff-matches-specjudgedThe change does what its piece and the spec say.
  • skeptic-reviewjudgedA skeptic, who can only object, finds nothing blocking.
  • journeys-passmechanicalEach kind of user’s main jobs work in a browser, on phone and desktop.

When it fails, the ladder

  1. Retrywith the objection quoted
  2. Send back or shrinkthe piece
  3. Parkit and revert it
  4. Stopand say why

Parked work is reverted, so it never ships, and the rest of the build carries on. On a real run the reviewer caught a loan that could never end, and the skeptic caught a removed neighbour who could rejoin.

Safe to ship guards the moment your app goes live.

  • journeys-passmechanicalEvery journey runs again, on a brand-new database.
  • preview-healthymechanicalThe preview serves the new build, not a login page or the old one.
  • rollback-verifiedmechanicalGoing back to the previous release actually works.

When it fails

Nothing is promoted. If a promotion fails after all, the app goes back to what was live, so a broken release never stays up.

Cost

Cost is a gate, not a surprise.

Every step has a zero-dollar path. Karigor estimates three tiers and asks you to pick one, exactly once. A running meter shows what has been used.

Free

A free local model for everything. Costs nothing; slower and less reliable, so expect more parked items.

Cheap

The cheapest cloud model for everything. Good for small, simple ideas.

Best

The strongest model for decisions and reviews, the cheap one for routine work. The best chance of a working result.

If the budget runs short, Karigor downgrades the model first, then parks optional work, then stops. Fix rounds after release have their own slice.

What gets built

A real web app, on a stack you could hire for.

Every web app starts with tested sign-in for many people, roles and permissions, an activity log and a UI kit of sidebars, tables, charts and dialogs. Tests, lint, build and journeys pass before the first feature is written.

Bigger ideas are split into stages. Stage 1 is the smallest version someone can use end to end; karigor grow builds each next stage on top of what is live.

Start with the demo: a scripted crew with no model and no cost, so you can watch the whole process end to end. Then pick the engine you want.

Needs Node.js 22 or newer and git.

git clone https://github.com/kishormorol/karigor
cd karigor
pnpm install && pnpm build

node packages/cli/dist/bin.js new "A site where neighbours lend each other tools" \
  --adapter demo --run
